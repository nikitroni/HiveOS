# HiveOS review and collaboration workflow

## Scope and status

- Read-only runtime-code audit completed for BeeOS, LabOS, HeartOS, deployment, and installation.
- Runtime fixes below are proposals awaiting discussion; none are implemented.
- This document is the only file added by the audit.
- Existing user changes to `.gitignore` must be preserved.
- No Minecraft execution, deployment, commit, or push was performed.

## Source ownership

- `0/`: BeeOS runtime sources.
- `1/`: LabOS runtime sources.
- `2/`: HeartOS runtime sources.
- `BeeOS/`, `LabOS/`, `HeartOS/`: publication mirrors generated by `deploy.bat`.
- Do not edit mirrors independently or stage numbered folders.
- Do not modify `_test/`, `_paint/`, `logs/`, or `backups/` without explicit authorization.

## Proposed implementation sequence

1. Make publication reliable: check every copy result, correct delayed variable expansion, and control staged changes before committing.
2. Make bee transfers recoverable: persist operation identity before moving items, retain partial progress, and acknowledge receipt and completion.
3. Make restart recovery distinguish unavailable peripherals from empty inventories; prevent new requests from replacing active tasks.
4. Make configuration saves and acknowledgements truthful; handle unfreeze failures and protect every update path while busy.
5. Guarantee redstone cleanup on errors and termination; validate resources before irreversible transfers.
6. Harden the installer against partial downloads and write failures; use one immutable revision per installation.
7. Refactor duplicate configuration screens and obsolete helpers, then address formatting and UI cache defects separately.

## Agent workflow

1. User describes the desired behavior and constraints.
2. Coordinator restates the expected result, inspects affected code, and asks only questions that affect implementation.
3. Record the agreed scope, acceptance criteria, ownership, and verification steps in a dated plan.
4. After agreement, delegate independent work with explicit file ownership:
   - BeeOS agent: `0/`.
   - LabOS agent: `1/`.
   - HeartOS agent: `2/`.
   - Coordinator: integration contracts, deployment, installer, review, and verification.
5. Define cross-role message schemas and state transitions before parallel implementation. No two agents edit the same file concurrently.
6. Agents implement and report changes, checks, and unresolved risks. Coordinator reviews the integrated result.
7. Hand over one runnable milestone with concrete Minecraft checks. User tests and reports results before moving to the next dependent milestone.
8. Commit and publish through the reviewed deployment flow only when requested by the user.

Small changes do not require three agents. Assign only the roles needed for the task, and use independent review when useful.

## Verification priorities

- Partial send and partial return must retain the original hive and unfinished task.
- Restart with an unavailable reader must preserve saved state.
- Duplicate requests must not replace an active operation.
- A timeout must not mark an unfinished worker free.
- Failed config writes must not produce success acknowledgements.
- Termination and peripheral errors must leave controlled redstone outputs off.
- A failed mirror copy must stop before staging, committing, or pushing.
- A failed installation must not announce readiness to reboot.

Use focused mock tests for failure paths where available, followed by tests in the actual game. Do not claim game compatibility based on static review alone.

## Information needed before runtime edits

- Installed ATM10 version and relevant peripheral/mod versions when behavior depends on their APIs.
- Whether `0/1/2` are used directly by the running world or copied into it separately.
- Per-feature expected behavior, acceptance examples, and any operations that must remain manual.

## Rules worth clarifying later

- Git cannot restore unmirrored edits in ignored numbered sources; the current rollback wording needs to account for this.
- Existing rules differ on automatic commits versus commits by user command; use explicit user direction.
- Existing source formatting differs from the prescribed two-space camelCase style; keep formatting migrations separate from functional changes.
- Runtime-created config backups are existing program behavior and should be discussed separately from the prohibition on agent-created file backups.
